## 得到模型后必须一起确认

1. 任务标签：检测整个基地、引导灯，还是装甲板？类别顺序及训练标签是什么？
2. 文件：`.pt`、`.onnx` 还是已经为 SG2002 编译的 `.cvimodel`？是否有描述文件 `.mud`？
3. 网络输入：宽高、NCHW/NHWC、RGB/BGR、缩放/补边/裁剪、归一化、相机90°旋转顺序。
4. 输出与后处理：输出节点、置信度定义、框解码、NMS、阈值、卡尔曼滤波、目标选择与失锁状态。
5. 运行环境：SDK、推理运行时、转换工具版本、芯片目标与量化校准样本。MaixCAM 与 Nano 硬件相关不等于镜像/SDK 无条件互换。
6. 许可与来源：允许怎样使用，权重与代码的许可是否一致；记录字节数与 SHA256。

**不执行来源不明的模型加载代码或 pickle。** 未经审查不运行上游脚本、不安装依赖、不刷固件。原生 `.pt` 不能当成板端 NPU 文件直接使用；通用 ONNX 也不意味着已经适配 NPU。

## 帧率应分开记录

| 指标 | 测量边界 | 不能混淆成什么 |
|---|---|---|
| 采集 FPS | 单位时间不同帧 ID / PTS 的取帧数 | 模型吞吐量 |
| 单帧推理耗时 | 明确是否含预处理、拷贝和同步的模型调用耗时 | 整链路端到端延迟 |
| 检测结果 FPS | 单位时间产生新结果的帧数，不计重复结果 | 采样率或显示帧率 |
| 端到端延迟 | 从曝光/PTS 对应时刻到结果可消费，时基需统一 | `1/FPS` |
| 图传/显示 FPS | 网络/客户端实际新画面数 | NPU 识别 FPS |

串行处理可用 `T≈取帧+预处理+推理+后处理` 做耗时分解；流水线吞吐量通常受最慢阶段约束，而总延迟仍含多阶段时间。开启双缓冲可能提高吞吐量但增加结果年龄，应测量而不是按公式保证。

**1280×720 采集 + 320×224 推理，不是 720P 神经网络推理。** 缩小全图可能使 20–30 m 的小引导灯消失，需同时记录原图/输入图上的目标像素尺寸，不以快但看不见目标的配置作为成功结果。

## 推荐的实测矩阵（尚未执行）

先离线重放同一批带标注的实拍图像，再在固定相机上做板端测试。不连接或控制发射装置。

| 组合 | 目的 |
|---|---|
| 仅采集 | 现有约 80 FPS 基线复核 |
| 采集 + 传统检测 | 基础对照，不依赖模型 |
| 采集 + 模型 + 必要后处理 | 真实模型识别性能 |
| 上述组合 + 录制 | 录像开销与结果留存 |
| 上述组合 + 推流 | 图传开销和客户端观测；不得误认为模型速度 |

各组合记录实际相机配置、模型哈希/输入尺寸、温度、CPU/内存、取帧数、结果数、P50/P95耗时、队列长度、丢帧与结果年龄，分别报告稳定段及启动段，不能只截瞬时最大 FPS。

稳定性至少看：正确目标检出率、误锁其它绿光次数、每段最长失锁时间、中心定位误差/抖动、遮挡后重获时间。覆盖 20/25/30 m、不同照明、白灯/绿色干扰、无目标、多目标和晃动。可用性阈值需根据实际任务确定，本次不无依据预设通过线。
