# GC4653 / SG2002：CAM1 分频 33（约 36 MHz）实机 A/B 画质实验

日期：2026-10-23（主机时间；板端系统时钟不可信）。设备：LicheeRV Nano SG2002 + GC4653。

> **重要结论：成功完成约 36 MHz 的 CAM1 硬件分频对照，1280×720 实际采集速率约 80 FPS，单张未压缩 Bayer RAW 顶部异常亮行消失，JPEG 顶部紫红异常大幅减轻。仅是短时研发试验，不是通过 10 分钟长测的正式无花屏驱动。**

## 1. 测试方法：绕过不支持 36 MHz 枚举的旧 CIF 驱动

- 原板端 Linux：`5.10.4-tag-`，`soph_mipi_rx` 原模块保留。
- 时钟父源：`clk_cam0pll=1,187,999,988 Hz`。
- 根据 SoC 时钟寄存器源码：`CLK_CAM1_SRC_DIV` 地址 `0x030028c4`，分频字段 `[21:16]`。
- 原寄存器：`0x00200001`，分频 **32**，对应 **37.125 MHz**（Linux 调试读数 37,125,000 Hz）。
- 实验寄存器：`0x00210001`，分频 **33**，对应 **35,999,999.64 Hz**（根据父时钟及寄存器计算）。
- 程序使用历史 GC4653 720P/80 档初始化表，启动约 7 秒后更改**CAM1 专用分频寄存器**，同时采集真实 VI、PTS 帧率与 Bayer RAW。
- 该方法仅是 **运行态 MMIO 对照试验**：不是重新编译并启用官方 36 MHz 时钟枚举；存在 Linux Common Clock Framework 与寄存器直写状态不同步的风险，**不可长期用作生产启动方式**。
- 特别说明：内核 `/sys/kernel/debug/clk/clk_cam1/clk_rate` 在寄存器改为 33 后仍读出 **37,125,000 Hz**。因此当前只能通过寄存器读回、父时钟和实际帧率变化共同推断分频已生效，**没有示波器直接测量 GC4653 MCLK 引脚波形**。

## 3. 真正 RAW 顶部画质对照

本次运行设置 `PREVIEW_DIAG_RAW=1` + `PREVIEW_DIAG_LINEAR=1`，以便记录完整 packed RAW12（每两像素3字节，1280×720×1.5=1,382,400字节），不是之前单次压缩 Bayer 输出的 691,200 字节。

使用 `analyze_raw.py` 按厂家 MaixPy 示例方式 unpack：每组三字节还原 2 个 12bit Bayer 像素。对比图片各自行20至80的平均亮度中位数，将顶部行的均值相减（**相同归一规则，无修图、插帧或裁掉坏行**）：

| Bayer 原始行 | 基线异常增量 | 分频33后异常增量 |
|---|---:|---:|
| 第0行 | -6.0 | -0.8 |
| 第1行 | +50.1 | +2.7 |
| **第2行** | **+127.5** | **-2.0** |
| **第3行** | **+126.4** | **+3.1** |
| 第4行 | +4.0 | 约 0 |
| 第5行 | +1.3 | +4.2 |

JPEG（仅作为视觉辅助）的前7行紫红像素阈值统计（R>120、B>85、G<100、R-G>55、B-G>25）：
- 分频32：`68, 120, 85, 68, 9, 0, 0`。
- 分频33：`0, 0, 0, 0, 0, 0, 0`。

**解释：** 在本次两张不同时间/姿态的 RAW 样本中，原来集中在顶部第1～3行的异常高亮峰值在约36 MHz 样本消失；JPEG 的紫红顶边也明显改善。现场画面曾被移动、曝光与ISP可能变化，因此这不是逐帧全场景的最终画质验收。

## 4. 其他实际运行记录

- 第一次仅切换分频2秒后恢复：寄存器成功读回，但 debugfs 仍报告37.125MHz；PowerShell 输入末尾回车符使 SSH Shell 返回127，然而 **原寄存器成功恢复**，不是带图像的成功测试。
- 第二次含压缩 Bayer 的 A/B：从约82.5下降到稳定约80 FPS，JPEG与691200字节压缩 RAW 均保留在 `results/`。期间 HTTP 单客户端占用使第一次取图失败，实验未进入分频33；随后已改为直接保存本地图像避免依赖 HTTP。
- 第三次（本报告重点）取消 Bayer 压缩，获得两份完整 packed RAW12，分频33期间 MIPI 错误计数保持不变，成功正常停止。
- 正常停止后验证：`devmem 0x030028c4 32` 为 **0x00200001**；debugfs `clk_cam1` 为 **37125000**；`/code/camera/run/lock` 不存在。
- 另外准备了一个长时间版本（`camera_36long.cpp`、`run_board_long.sh`），但**执行动作被工具安全检查阻止，未实际开展连续60秒/10分钟测试**，绝不能标记为完成。

## 5. 结论与下一步

**已验证：** 在用户态临时修改分频的短时运行下，真 VI/PTS 约80 FPS，1张 RAW 和 1张 JPEG 画质明显较超规格时钟改善，运行阶段无新增 MIPI 错误；原驱动、固件、原封存实验均未替换。

**尚未验证：** 物理 MCLK 引脚波形、厂家针对36 MHz的完整 PLL/MIPI/曝光初始化表、所有温度/曝光/场景下的 RAW 画质、连续10分钟零错、与 Linux CCF 一致的正规时钟驱动及持久化启动方式。

后续正确路线：将同样的 36 MHz 分频操作移入经 ABI 验证的 **soph_mipi_rx 驱动**，让内核 `clk_set_rate` / `clk_get_rate` 与实际寄存器一致；厂家高速寄存器与 ISP/AE 时序配套，再做连续10分钟 RAW 采样、MIPI监视、温升测试。避免把用户态 `devmem` 试验永久写入自启动。
