## 2. 时钟验证范围和回退

- 旧 CAM1 divider MMIO `0x030028c4 = 0x00200001`：CAM0PLL（1,187,999,988Hz）÷32 = **37.125MHz**。
- **本次测试** `0x00210001`：分频33，根据父时钟计算 **35,999,999.64Hz**。实机寄存器读回已核实，且采集帧率降低至约80 FPS，符合预期。
- Linux `debugfs/clk_cam1/clk_rate` 在直接写寄存器之后依然报告 `37125000`，与分频寄存器推算不一致。**并没有测量 GC4653 MCLK 引脚的实际波形**，因此只称“约36MHz分频方案”。
- 运行自带超时300秒、SoC 74.5°C阈值、相机独占锁、MIPI错误变化监测、SIGTERM清理、临时硬件看门狗（约335秒）和正常退出时恢复寄存器。
- **最终板端实测：** `devmem 0x030028c4 32 = 0x00200001`，`clk_cam1=37125000`，锁目录不存在，相机程序已经退出。
- 未替换原有 `soph_mipi_rx.ko`，未修改原始 `/code/camera/bin`，未写入自启动项。

## 3. Bayer RAW12 顶部条纹复核

这次在同一实验过程中采集了 **before、after、late** 三张未经压缩的 1280×720 packed RAW12，每张 1,382,400 字节，且是 ISP 前的 Bayer 数据。

对每张图以行20～79平均亮度的中位数作为参考，得到顶端行的平均亮度偏差：

| 传感器 Bayer RAW 行 | 37.125MHz 初始基线 | 分频33刚切换后 | 分频33约55秒后 |
|---|---:|---:|---:|
| 第2行 | **+78.602** | −2.155 | −3.928 |
| 第3行 | **+53.358** | −13.008 | −12.731 |

初始样本顶部突发亮行在切换后与约55秒后的 RAW 抽样中均明显改善。JPEG 预览画面也已实际抓取并查看，未见之前大面积紫红色条纹。

**限制：** 这只是三张 RAW 抽样；虽然 5 分钟内 MIPI 错误和帧率稳定，仍没有完整逐帧RAW画质审核，也没有覆盖运动、曝光、亮暗场、散热变化、不同模块等全部情况。尤其不能直接宣称“5分钟每一帧绝对无彩条”。

## 6. 下一步

当前仍存在一个关键工程风险：**直接写 MMIO 改 CAM1 时钟会让 Linux Common Clock Framework 的软件状态与硬件状态不一致。** 正式驱动应取得与板端 `5.10.4-tag-` 对应的 BSP/ABI，改为内核时钟 API 申请和回读准确的36MHz，验证 GC4653 模组 MCLK 引脚波形与厂家高速初始化表，进一步完成至少10分钟逐帧画质与热稳定性验收。

> 这套脚本是开发板实验代码，不应作为无需看护的长期监控或生产驱动部署。请勿照抄到其他开发板或在相机被其他进程占用时强行改寄存器。
