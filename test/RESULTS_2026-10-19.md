# 2026-10-19 GC4653 高帧率实验结果

结论：1080P Factory 方案通过小幅调整行时序从 66.00 FPS 提升到 68.79 FPS；尚未满足“超过 80 FPS 且无彩条”。测试全部保存于 D:\study\LicheeRV\test。

| 1150 | 0 | - | - | 持续 Operation not permitted | - | 69.27°C | 失败、零帧；停止后续更激进测试 |

验证范围：每档约16秒运行，头4秒为预热；非数小时稳定性测试。仅通过 JPEG 原图、NV21顶部统计和内核/PTS计数粗筛条纹，不能证明所有帧/所有位置绝无瑕疵。JPEG Q95 属有损压缩，不是数学无损。

来源与记录：
- results/hts-experiment-20261019-retry1/summary.json 保存 1250、1200 的实时采集数据、RAW和JPEG。
- results/hts-experiment-20261019-retry1/quality.json 记录顶部相邻行亮度差：旧1080原图最高比值1.241，HTS1250为1.040，HTS1200为1.054；旧坏80档历史值约26倍。
- results/hts-experiment-20261019-step2/summary.json 以及 hts-1150/run.log 记录零帧和失败日志。原先首次脚本因锁等待逻辑失败，未实际开始测试，记录位于 results/hts-experiment-20261019/。
- results/factory-restored-after-hts/report.json：恢复后1920×1080视频流成功接收，6秒87帧，接收FPS约14.8（不是传感器FPS）。

恢复状态：已通过原有 stop/start-preview-factory.sh 正常恢复 board 的 camera_preview_factory 60 进程，且复查 HTTP 视频端点能返回完整 JPEG。没有替换/删除任何历史源码、程序或板端驱动。新板端实验放在 /tmp/lichee-camera-test，仅在电脑的 test 目录中保存新增和改动的研发文件。

背景：官方 https://wiki.sipeed.com/maixpy/doc/zh/vision/camera.html 列举 GC4653 常见 720P 60/80 档，警告部分模组在80FPS会出现异常纹路；本板历史 speed-fry/stripe-diagnostic/REPORT.md 已在 ISP 之前 Bayer RAW 复现 80 档彩条。旧报告不能当成此次已修复的证明。

设计判断：HTS 1250->1200 短时提速约4.22%；继续到1150时完全无法采集，提示当前传感器读出/接收时序存在界限。没有足够依据继续把行时序压到能超过80FPS。更高帧应优先寻找GC4653合法独立高速window、PLL/MIPI同步表以及板端硬件信号问题证据，再受控实验。

新增文件：factory_timing/ 下的独立源码、build.sh、rebuild-sensor.sh 和 RISC-V ELF；run_hts_experiment.py、run_hts_experiment_step2.py、analyze_hts_quality.py 和 results/ 内的日志图像。首次编译缺头文件及 getenv 声明已在 test 里修复。
